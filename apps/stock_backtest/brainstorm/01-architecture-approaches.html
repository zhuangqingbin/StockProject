架构方案对比

选择回测平台的整体架构模式

A

单体服务 + 异步队列

一个 FastAPI 服务处理所有请求，回测任务通过 Celery + Redis 异步执行

React Frontend
策略配置 / 结果展示 / 对比分析
FastAPI Backend
API + WebSocket + 策略管理
Celery Worker
Backtrader 回测执行
存储层
MySQL (数据+结果)
Redis (队列+缓存)

优势

  • 架构简单，部署方便
  • 和现有 stock_bi 模式一致
  • 异步执行不阻塞 API

劣势

  • 需要额外维护 Redis
  • Worker 扩展能力有限
B

单体服务 + 进程池

FastAPI 服务内置 ProcessPoolExecutor，回测任务在子进程中执行，无需额外中间件

React Frontend
策略配置 / 结果展示 / 对比分析
FastAPI Backend
API + WebSocket + 策略管理
ProcessPoolExecutor
Backtrader 子进程回测
存储层
MySQL (数据+结果)

优势

  • 最简单，无额外依赖
  • 部署只需一个服务
  • 小团队完全够用

劣势

  • 服务重启会丢失运行中的任务
  • 无法分布式扩展
C

微服务拆分

API 服务、回测引擎、数据服务各自独立，通过消息队列通信

React
API Service
Backtest Engine
Data Service
MQ + MySQL

优势

  • 各服务独立扩展
  • 架构最清晰

劣势

  • 小团队过度工程化
  • 运维复杂度高
  • 开发周期长

💡 推荐：方案 B

对于小团队使用场景，方案 B 最务实 — 零额外依赖，部署简单，性能对几个人同时使用完全够。回测任务通过 ProcessPoolExecutor 在子进程执行，不阻塞 API。任务状态持久化到 MySQL，即使服务重启也能查看历史结果。未来如果需要，可以平滑升级到方案 A。
